History of conda-forge

From compiling everything by hand to 30,000+ packages

Context

Python packaging before conda

  • Early 2010s: Python 2.x was the norm; installers came from python.org, Python(x,y), ActiveState, or Enthought's EPD/Canopy
  • The community was moving from easy_install/eggs to pip, but there was no easy way to ship pre-compiled packages
  • Wheels weren't formalized until 2013 (PEP 427); on Windows, Christoph Gohlke's builds were often your only option
  • Linux users had to compile from source — manylinux wheels didn't exist until PEP 513 in 2016
Binary compatibility

Why building from source was the default

numpy 1.7.0 (Feb 2013)

Only a few Windows .exe installers, no macOS wheels, no manylinux wheels — those didn't land until April 2016.

numpy 1.11.0 (Mar 2016)

Wheels for all platforms.

Binary compatibility depends on matching compiler + core library (glibc) versions between the build machine and the destination machine. Linux distros freeze these per release, which is why cross-distro binaries are fragile.
Origins

Enter conda (2012–2013)

  • 2012: Continuum Analytics announces Anaconda 0.8 at SciPy; in September, conda 1.0 ships as a cross-platform, language-agnostic package manager for pre-compiled artifacts
  • conda packages could ship compiled shared libraries and Python itself, not just Python code
  • By June 2013: conda gets a SAT solver, conda build ships, Miniconda and Binstar.org (hosting for user-built conda packages) launch
…at the first PyData meetup at Google HQ, where several of us asked Guido what we can do to fix Python packaging for the NumPy stack. Guido's answer was to ‘solve the problem ourselves.’ We at Continuum took him at his word… and created the conda package manager and conda environments.

Travis Oliphant, Why I promote conda (2013)

2014

From shared recipes to fragmented channels

  • ContinuumIO/conda-recipes became the central place to contribute conda recipes — but quality varied, most recipes only worked on 1–2 platforms, and there was no CI
  • Groups adopted Binstar/Anaconda.org for their own needs: Omnia (Molecular Dynamics, Mar 2014), the Met Office's SciTools (Jun 2014), IOOS (Jul 2014)
  • Phil Elson (SciTools) built CI + tooling (conda-build-all); Filipe Fernandes (IOOS) borrowed it — lots of cross-pollination, but duplicated recipes and unpredictable compatibility when mixing channels
Milestone April 11, 2015

conda-forge is registered as a GitHub organization and an Anaconda.org channel

Growing pains

The toolchain overhaul

  • GCC 5 shipped a breaking libstdc++ change; the aging CentOS 5 / GCC 4.8 toolchain made building cutting-edge projects (e.g. early TensorFlow) painful
  • The community chose to build and ship its own GCC toolchain as conda packages, instead of relying on Red Hat's devtoolset
  • Result: conda-build 3's compiler(...) Jinja function, the build/host/run dependency split, and dynamic pinning — funded in part by Samsung and Intel contracts with Anaconda
  • This eventually produced the main channel: conda-forge recipes built with the new shared toolchain

How to submit your own recipe

Your package's front door: conda-forge/staged-recipes

Overview

staged-recipes: the front door

  • staged-recipes is a holding area for recipes destined to become their own feedstock — every package on conda-forge went through it
  • Flow: fork → branch off main → add a recipe under recipes/<your-package>/ → open a PR → CI builds it on Linux/macOS/Windows → review → merge
  • Once merged, CI automatically creates a new <package>-feedstock repo and triggers the first build
Getting started

Generating a recipe

Use a generator

Python packages on PyPI — grayskull pypi --use-v1-format <package>. R packages on CRAN — the conda_r_skeleton_helper script.

Start from the example

Anything else — copy recipes/example-v1/recipe.yaml and edit by hand, following the section order and removing the explainer comments.

Example

Anatomy of a recipe

recipe/recipe.yaml 
context:
  version: "3.8.2"

package:
  name: simplejson
  version: ${{ version }}

source:
  url: https://pypi.org/packages/source/s/simplejson/simplejson-${{ version }}.tar.gz
  sha256: d58439c548433adcda98e695be53e526ba940a4b9c44fb9a05d92cd495cdd47f

build:
  script: python -m pip install . -vv
  number: 0

requirements:
  host:
    - python
    - pip
    - setuptools
  run:
    - python

tests:
  - python:
      imports:
        - simplejson
      pip_check: true

about:
  homepage: https://github.com/simplejson/simplejson
  license: MIT
  license_file: LICENSE.txt
Note the ${{ ... }} Jinja-in-YAML syntax. The sha256 should come from the tarball itself (curl -sL <url> | openssl sha256), never a repo checksum.
Dependencies

requirements: build / host / run

Section What goes here Typical examples
build Tools needed only while building, not on the host Compilers, cmake, make, pkg-config
host Present alongside the package at build time Shared C/C++ libraries, python/r-base, pip, setuptools
run Needed only when the package runs Most Python/R runtime libraries
As a rule, all dependencies must themselves be packaged on conda-forge, to guarantee ABI compatibility across the ecosystem.
Quality bar

Every recipe needs tests

  • At minimum: existence tests — verify the package installed the files you expect (package_contents in v1)
  • Python packages: a python: test with imports: + automatic pip_check: true
  • R packages: an r: test with libraries:
  • Command-line tools: run <tool> --help to prove it's on PATH and executable
  • The goal is testing that the conda package built and installed correctly — not re-running the upstream project's full test suite
Checklist

Before you open the PR

  • License uses the correct SPDX identifier and case (Apache-2.0, not APACHE 2.0)
  • A license_file is included, unless the upstream tarball already ships one
  • Build from a tarball (url:), never git_url: — tarballs are checksummable and smaller
  • Remove the example's explainer comments from your copy of the recipe
  • Leave the recipes/example-v1/ folder itself untouched
What happens next

Review → merge → feedstock

Getting reviewed

Mention the appropriate language team (e.g. @conda-forge/help-python) in a PR comment; first-time contributors can ask a bot to ping the team for them.

After merge

CI creates <package>-feedstock automatically, triggers the first build, uploads to anaconda.org/conda-forge, and invites you to the conda-forge GitHub org with commit rights on your new feedstock.

What's next

Congrats, you're a maintainer

  • Merge routine maintenance PRs opened by conda-forge's bots
  • Bump the version + checksum whenever upstream releases
  • Keep requirements accurate as the package's dependencies change
  • Answer questions on the feedstock's issue tracker
None of this works without the volunteers reviewing every PR that comes through staged-recipes — that's our next section.

Get involved: review staged recipes

The community that keeps the front door open

Why it matters

staged-recipes always needs reviewers

  • It's one of the highest-traffic repos in conda-forge — every new package waits here for a review
  • Review times vary from days to weeks depending on how many volunteers are active on a given language team
  • Straight from the maintainers: “We are always looking for more staged-recipe reviewers”

The gap

Why C/C++, R, and Java need you

  • These ecosystems tend to have more compiler-heavy, platform-specific build logic (native toolchains, Rtools/CRAN quirks, JDK/build-tool versioning) than pure-Python recipes
  • Fewer reviewers are comfortable evaluating those recipes, so PRs in these languages wait longer
